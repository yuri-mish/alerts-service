# alerts-service — контекст і правила для Claude

Сервіс на VPS щодня бере з alerts.in.ua історію повітряних тривог по регіонах і веде базу Postgres;
дає HTTP-ендпоінти: запустити оновлення, отримати дані. Спілкування з користувачем — українською.

## Стан (15.11.2026)
- Код написаний, 21 інтеграційний тест зелений (на Postgres VPS). Сервіс **запущено** на VPS (`docker compose`) і працює
  публічно: лендінг з графіком і формами, адмінка `/admin`, клієнтські ключі, Telegram-бот, монітор, Google Analytics.
- **Відкриті питання (користувач відклав):** безпека бази (деталі — `CLAUDE.local.md`); бекапи лише на тому ж VPS; блокування за IP (5 невдалих ключів/год) може зачепити офіс разом з 1С;
  немає зовнішнього пінгу `/health`; на VPS лишились `.env.bak-admin-rotation` і невикористаний `UKRAINEALARM_TOKEN`.
- Регіони в `regions` (з 14.11.2026 — **усі області**, UID з таблиці alerts.in.ua): 3–5, 8–15, 17–28, 31.
  **Не додавати 16 (Луганська), 29 (Крим), 30 (Севастополь)** — вимога користувача: там «вічні» тривоги з 2022.
  Прогін ~24 регіони × 31 с ≈ 12–13 хв; база ~20 тис. тривог/місяць (~670/добу); фактично (26.11.2026) ~380 Б на тривогу з відрізком та індексами →
  ~7–8 МБ/міс, ~90 МБ/рік (БД 20 МБ, з них ~9 МБ — службове; бекап 1,2 МБ).
  Регіон 31 — лише сам м. Київ; у 9 (Дніпропетровська), 22 (Харківська), 15, 12 окрім районів є громади (`hromada`)
  і міста (`city`) — перекриваються з районами (`alerts` у `/summary` рахує їх усі, години — з об'єднанням перекриттів).
  **Це фіча, не баг** (користувач, 15.11.2026): не «виправляти» і не пропонувати пояснення чи фільтри.
- Назва — **«API історії повітряних тривог»** (16.11.2026): упор на **історію**; тривоги, що ще тривають (стан на нічне
  оновлення, кінець null), — лише бонус, реальний час не обіцяємо. Так у title лендінгу/docs, OG, OpenAPI.
- Лендінг: сервіс **для всіх систем, 1С — пріоритет** (вимога користувача, 15.11.2026): «Історія повітряних тривог

- Графік на лендінгу «Тривоги за останні 30 днів» (під шапкою): ранжовані горизонтальні стовпчики по регіонах,

  їх раз на 30 хв досилає монітор (`resendContactMessages`, позначка «доставлено із запізненням») і теж видаляє. Обидві форми — спільна `setupFormDialog` у лендінгу.

## Вимоги користувача (вже реалізовані — не змінювати без запиту)
- Node 24 + вбудований TypeScript (type stripping): `node src/main.ts`, `tsc` лише для перевірки типів.
  Тому: без `enum`, `namespace`, parameter properties; імпорти з розширенням `.ts`; `import type` для типів
  (tsconfig: `erasableSyntaxOnly`, `verbatimModuleSyntax`, `allowImportingTsExtensions`, `noEmit`).
- Регіони в окремій таблиці `regions` (31 — м. Київ, 14 — Київська обл., 27 — Львівська, 10 — Житомирська).
- **Рахуємо лише `alert_type = 'air_raid'`** (вимога користувача, 14.11.2026): інші типи (`artillery_shelling`,
  `urban_fights`, …) зберігаються в `alerts`, але в `alert_periods` (а отже в `/periods`, `/summary`, `/1c/alerts`)
  не потрапляють — фільтр `REPORT_ALERT_TYPE` у `rebuildPeriods`.
- У відповіді API є підрегіони (райони, громади, напр. `location_uid: "94"` — рядок!) — зберігаються як `location_uid`;
  `region_uid` = регіон, за яким робили запит. `oblast_uid` не зберігаємо (прибрано за запитом).
- Фільтри `/periods`, `/summary`, `/1c/alerts`: `region`, `location` — одне значення або список через кому.
  **Обов'язковий лише `month`** в усіх трьох (вимога користувача, 26.11.2026; інакше 400 `month: required (YYYY-MM)`);
  **без `region` і `location` — усі області** (до 26.11.2026 територія була обов'язкова). Обсяг — один місяць
  (вся країна: ~20 тис. рядків, ~0,1–0,3 с у БД, `/periods` ~7 МБ JSON).
  Схеми рядка запиту — `z.strictObject`: **невідомий параметр → 400** (`Unrecognized key`). `/1c/alerts` має `level`
  (16.11.2026); `НомерТревоги` рахується по всіх тривогах доби **до** фільтра level (інакше два «№1» в одній добі).
  Тіла запитів не суворі — форми шлють поле-пастку `website`.
- Раз на добу (03:30 Київ, `SYNC_TIME`) бере дані за місяць і актуалізує БД. **Опитування активних тривог НЕ треба** (користувач відмовився).
- Таблиця для звітів `alert_periods`: регіон, рівень (жовтий/червоний), доба (`day`), місяць, початок, кінець, тривалість у хвилинах.
- Тривога на межі **доби** (а отже й місяця) — **розрізати на частини** по київській півночі (вимога користувача, особливо для 1С).
  Тривога без кінця лишається одним відкритим відрізком у добі початку. PK `(alert_id, day)`.
- `/1c/alerts` — вигрузка для 1С (`ПериодМесяц, ДеньМесяца, КодТеритории, ТипСобытия, НомерТревоги, Начало, Конец`):
  рядок на добу тривоги; `НомерТревоги` — порядок у межах території й доби; час київський ISO.
- Після зміни логіки розрізання: `npm run rebuild` (перебудова `alert_periods` з `alerts`; таблиця похідна).
- **Зміни рівня тривоги НЕ відстежуємо** (вимога користувача, 13.11.2026; раніше було «закрити один рівень, відкрити
  другий» через таблицю `alert_levels` — прибрано). Зберігається лише останній відомий рівень
  `alerts.level`; одна тривога = один відрізок на добу з цим рівнем.
- `/summary`: години — об'єднання інтервалів; активна тривога (без кінця) рахується до поточного моменту
  (інакше `range_agg` з відкритим кінцем «з'їдає» години перекритих закритих тривог).
- Тривога, що «висить» активною понад **3 доби** (72 год, `STALE_AFTER_H`; до 14.11.2026 було 24 год) — закривається як **початок + 30 хв** (`closed_by = 'stale_30min'`);
  якщо API потім дасть справжній кінець — замінює.
- HTTP-ендпоінти: оновити дані, отримати дані (див. README.md).
- **Публічний сервіс, лише API** (14.11.2026): ключ адміністратора — env `API_KEY` (усе); клієнтські ключі — таблиця
  `api_keys` (зберігається лише sha256), відкрито тільки `GET /periods`, `/summary`, `/1c/alerts`, `/alerts/{id}`,
  ліміт `RATE_LIMIT_PER_MIN` (6/хв, вимога користувача) на ключ у пам'яті процесу. Керування: `GET/POST /keys`, `PUT /keys/{id}` (адмін).
  Ключ адміна (env `API_KEY`) — той самий 10-символьний, він же клієнтський №2 (1С). **НЕ міняти ключі без прямого
  запиту** (15.11.2026 я замінив без дозволу — користувач велів повернути, повернуто).
  Усі відповіді мають заголовки безпеки — **helmet** (16.11.2026): стандартний набір + `X-Frame-Options: DENY`,
  CSP **лише** `frame-ancestors 'none'` (повний CSP зламав би GTM і вбудовані скрипти лендінгу), `Referrer-Policy:
  strict-origin-when-cross-origin`, `Cross-Origin-Resource-Policy: cross-origin` (API для інших сайтів), HSTS 1 рік. Вебхук Telegram при невдачі реєструється повторно у фоні (1, 2, 5, 10, далі кожні 30 хв).
  Захист від підбору: 5 невдалих ключів з IP (`X-Real-IP`) → блок до кінця годинного вікна (429), навіть з правильним
  ключем; запити без ключа не рахуються. CORS `*`. На `GET /` — лендінг `src/site/landing.html` (опис сервісу, `/periods`, `/summary`, `/1c/alerts` з прикладами
  curl/JS/1С), без ключа; при зміні API/лімітів/регіонів — оновлювати і його. Вгорі плашка «безкоштовно, тестовий режим».
  Для пошуковиків (`src/site/site.ts`): `/robots.txt` (закриває шляхи API, крім `/stats` — інакше Google рендерить лендінг без графіка), `/sitemap.xml`, `/favicon.svg`, `/og-image.png` (og:image 1200×630), `/hero-bg.jpg` (фон шапки лендінгу), canonical,
  OG-теги, JSON-LD (WebSite + WebAPI), `/llms.txt` (`src/site/llms.txt` — опис для AI-асистентів; **оновлювати разом з
  лендінгом**); статичні сторінки відповідають і на HEAD. Перший клієнт (26.11.2026, Power BI, громади) прийшов з
  ChatGPT (`utm_source=chatgpt.com`) — тому на лендінгу акцент на громадах, тривалості, Power BI/Excel і вкладка Power BI. Google Search Console — за користувачем.
- Заявка на ключ: модальне вікно на лендінгу (Ім'я, Компанія — необов'язково, Для чого, Email) → `POST /key-requests`
  (без ключа, 3 з IP/год за `X-Real-IP`, приховане поле-пастка `website`) → таблиця `key_requests`
  і повідомлення користувачу в Telegram (`src/keys/key-requests.ts`; env `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`).
  Помилка Telegram не губить заявку (`telegram_error`).
- Рішення по заявці — кнопки в Telegram «✅ Прийняти» / «❌ Відмовити» (бот @alerts_keyreqest_bot, `src/notify/telegram.ts`,
  `key_requests`: `status` pending/approved/rejected, `decided_at`, `api_key_id`, `telegram_message_id`). Вебхук
  `POST /telegram/webhook` реєструється при старті (`PUBLIC_URL`, за замовч. https://alerts.starsam.net), секрет —
  sha256 від токена бота; кнопки приймаються лише від `TELEGRAM_CHAT_ID`. «Прийняти» створює клієнтський ключ.
  **Email не надсилається** (вибір користувача 14.11.2026: поки без пошти; пошта домену на Google Workspace) —
  адмін отримує в Telegram готовий лист (з ключем або з відмовою) і пересилає сам.
- Спостерігач (`src/notify/monitor.ts`, кожні 30 хв, лише якщо налаштований Telegram) пише адміну в Telegram **тільки про
  проблеми** і про їх зникнення: прогін `error`/`partial`/з попередженням; немає вдалого прогону > 26 год; найновішому
  `*.dump` > 26 год (тека бекапів змонтована в контейнер `/backups:ro`, docker-compose `volumes`). Нагадування — раз на
  12 год; стан у пам'яті (після перезапуску незакрита проблема повідомиться ще раз).
- Міні-адмінка `GET /admin` (`src/site/admin.html`; не індексується: заголовок `X-Robots-Tag: noindex` + мета-тег;
  **свідомо НЕ в robots.txt** — щоб робот бачив noindex і щоб не світити адресу адмінки): вхід ключем адміністратора (sessionStorage),

## API alerts.in.ua (перевірено)
- Історія: `GET https://api.alerts.in.ua/v1/regions/{uid}/alerts/month_ago.json`, `Authorization: Bearer <token>`.
  Лише останні ~30 днів, довільного діапазону дат немає. Ліміт історії — **2 запити/хв** (пауза 31 с між регіонами);
  загальний — 8–10/хв м'який, 12/хв жорсткий (429), систематичні порушення — бан IP/токена.
- `alert_level` (`red`/`yellow`) в історії **є** (підтверджено користувачем). `threats` в історії немає.
- Час — UTC ISO (`...Z`); `finished_at` = null, поки триває. 401/403 — зупинка прогону.
- Кешування: `If-Modified-Since` = значення `last-modified` з попередньої відповіді (не текст «Last-Modified»);
  `cf-cache-status: BYPASS` — Cloudflare не кешує, це нормально.
- Список UID: https://docs.google.com/spreadsheets/d/1XnTOzcPHd1LZUrarR1Fk43FUyl8Ae6a6M7pcwDRjNdA (75 = Бучанський район).
- Минулого до першого запуску з API не отримати. Волонтерський датасет
  github.com/Vadimkin/ukrainian-air-raid-sirens-dataset — лише області/Київ, без рівнів; офіційний там застарів (до 07.09.2026).

## Структура
Локальна папка: `C:/react/alerts-service` (на VPS — `~/projects/alerts`). Git є: `main` → https://github.com/yuri-mish/alerts-service (комітить користувач; **репозиторій публічний** — станом на 16.11.2026).

- `migrations/*.sql` — застосовуються при старті (`schema_migrations`). Усе зібрано в один `001_init.sql` (15.11.2026, зведено 001–007; звірено з робочою базою — схема й регіони ідентичні). У `schema_migrations` на VPS лишились записи старих файлів — нешкідливо.
  Нові зміни схеми — новим файлом `002_...sql`; `deploy.sh` перед заливкою чистить `migrations/src/test/scripts` на VPS.
- `src/` за теками (16.11.2026): у корені — лише точки входу (`main.ts`, `migrate.ts`, `sync-once.ts`, `rebuild-periods.ts`);
  `core/` (config, db, log, validation), `sync/` (alerts-api, sync, scheduler), `http/` (server, auth, common, openapi, handlers/),
  `site/` (site.ts, stats.ts, landing.html, docs.html, admin.html, favicon.svg, og-image.png, hero-bg.jpg), `keys/` (api-keys, key-requests),
  `notify/` (telegram, contact, monitor).
- `src/sync/alerts-api.ts` — клієнт API + `parseHistory` (нормалізація).
- `src/sync/sync.ts` — `applyAlerts` (пакетна вставка нових, оновлення змінених, без запитів у циклі для незмінених), `closeStale`, `rebuildPeriods` (розрізання в SQL
  через `generate_series` по добах у `TIME_ZONE` — env, за замовчуванням `Europe/Kyiv`, читається в `config.ts`: модуль читає env один раз при імпорті, усі беруть `config.timeZone` / `config.*`; `ALERTS_TOKEN`/`API_KEY` точка входу перевіряє через `requireConfig(...)` (єдине місце); в SQL передається параметром. Після зміни зони: `npm run rebuild`), `rebuild-periods.ts` (повна перебудова, `npm run rebuild`), `startSync` (pg advisory lock, `sync_runs`).
- HTTP — **Express 5** (вимога користувача, 16.11.2026; async-помилки Express 5 передає в обробник сам):
  `src/http/server.ts` — `createApp` (заголовки CORS/безпеки, OPTIONS→204, `express.json` для будь-якого Content-Type,
  роутери, 404, `handleError`: `HttpError`→його код, помилки тіла→400/413, інше→500) і `createServer` (`http.Server` для main/тестів);
  `src/http/auth.ts` — middleware `requireClientKey` / `requireAdminKey` (`createKeyGuards`) (ключ, ліміт на ключ, блок підбору за IP);
  `src/http/handlers/` — роутери `createPublicRouter` (сайт, `/stats`, `/health`, форми, вебхук), `createDataRouter`

## VPS
- **Репозиторій публічний** — адресу, порт і логін SSH, деталі Postgres/nginx та інших сервісів VPS тримати лише в
  `CLAUDE.local.md` і `.env.deploy` (обидва в `.gitignore`), не в файлах під git.
- Про `sudo` на VPS — див. `CLAUDE.local.md`.
- **На сервері щось вбиває (SIGKILL) процеси з паролем у рядку аргументів** — паролі/токени передавати через stdin
  або env, ніколи аргументом команди.
- Проєкт: `~/projects/alerts` (тут `.env.db` з `DATABASE_URL` і `.env` з `ALERTS_TOKEN`, `API_KEY`, `HOST`, `PORT`, `SYNC_TIME`; права 600).
  Секрети не виводити в консоль/чат.
- Postgres **18** на хості (не в Docker; оновлено з 16 — 17.11.2026 через `pg_upgradecluster`); контейнер у `network_mode: host`. nginx → `127.0.0.1:6020`, Let's Encrypt.

## Розгортання / перевірка
Скрипт: `npm run deploy` (або `deploy:fast` без тестів; `-- --logs` — стежити за логами) = `bash deploy.sh`:
заливка коду → `npm install` + `tsc` + тести на VPS → `docker compose up -d --build` → логи.
Куди деплоїти — з `.env.deploy` (`DEPLOY_HOST`, `DEPLOY_PORT`; зразок — `.env.deploy.example`). Ручні команди — у `CLAUDE.local.md`.
